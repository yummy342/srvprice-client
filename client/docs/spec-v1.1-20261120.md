## §0 总则

客户端是一个装在主流 agent 里的插件。用户用自然语言说一次意图，客户端自动跑完整流程；用户只做登录和确认；客户端没有自己的窗口，用户眼前只有两样东西：跟 agent 的对话，和自己的浏览器。

## §1 产品定位

1. 主角是客户端插件，不是网站，不是独立 App，不是侧边栏。
2. 网站冻结加功能，只剩三件事：门面、下载、给客户端供数据的公开接口（快照/推荐/ledger）。
3. 客户端的核心视图是资源列表；新手引导只是可选开关。

## §2 适配宿主（第一优先级）

1. 适配主流 agent：Muse、Claude Code、Codex、WorkBuddy。同一个客户端核心，按各家插件规范接入。
2. 用户用哪个 agent，客户端就长在哪个里，不用换工具、不用学新界面。
3. 第一期先做 Muse 宿主；第二期接 Claude Code / Codex。
4. 各宿主的 exact 安装命令待定，按宿主文档逐家核实后写入；**核实前规格不写具体命令**。

## §3 用户眼前的形态

1. 装机是两件东西：agent 插件（装进 Muse / Claude Code 里）+ 浏览器扩展（Muse 扩展 "Use this browser" 那种，接管用户自己的 Chrome/Edge）。
2. 用户不用打开任何新程序：打开平时用的 agent，说一句话（或打一行字），就开始了。
3. 用户看到的只有两样：跟 agent 的对话（语音或文字），和自己的浏览器（客户端自动打开页面，用户看得见每一步在哪）。查资源的结果由 agent 在对话里报出来，或直接显示在打开的页面上。
4. 实例（2026-11-20 凌晨真实流程）：用户说建火山只读账号，浏览器里自动打开火山控制台，语音一步步带用户点新建用户、选编程访问、挂只读策略，密钥当场存本地——用户只做了登录和点确定。
5. 没有独立 App、没有网站入口、没有侧边栏、没有弹窗表单；对话是主界面，浏览器是显示器。

## §4 交互方式

1. 语音优先：客户端在后台跑，需要用户时用语音叫一声，其余时间不用盯着。
2. 文字输入框并行：不方便语音的人用输入框，两种方式都能收到提醒、都能确认。
3. 语音提醒的触发点：需要人工时（登录、短信码、确认）和关键节点完成/失败时。**静默规则第一期固定为“需要人 / 完成 / 失败”三类触发**，其余不主动叫；后续再调。
4. 触发主路是自然语言，不用关键词、不用斜杠命令：用户说“我要去找服务器”“帮我查一下什么样的服务器更好”，agent 认出意图就直接调客户端。
5. 斜杠命令和“用 srvprice”只是备用，万一意图没认出来时用。
6. 打开 agent 不自动跑，不打扰。
7. **语音栈（2026-11-20 修正；2026-11-21 识别路线更正）**：系统 TTS 在本机是死的（0 个语音包，命令不报错但没声音，实测），不能当兜底。第一期的顺序改为：
   1. **播报：edge-tts 优先**（免费、中文自然，本机已装 7.2.7）；
   2. **识别：Python sounddevice VAD + faster-whisper**（本地、不花钱、不需系统语音包）；**whisper.cpp / stream.exe 仅作兜底**；
   3. 宿主语音（Muse）**待验证**：宿主要是有麦克风/STT/TTS 通道，以后优先走宿主，客户端只发文本；
   4. 装 Windows 中文语音包（SAPI）**只作兜底**，质量一般，不依赖。
   STT 仍然不在客户端里自建（用现成的 faster-whisper），也不要求四个宿主都支持语音。
   修订记录：2026-11-21 与 muse 验收时确认，实际实现已从 whisper.cpp 切到 faster-whisper（`tools/recorder_vad.py` / `tools/transcribe_fw.py`），本行同步更正。

## §5 半自动 pipeline

1. 用户只做两件事：登录（手机号/短信、扫码、密码）和最后确认（买之前点确定）。
2. 其余全部客户端自动完成：开页面、找入口、填信息、查状态、比价、准备下单。用户不用一步步指挥，不用口述流程。
3. 人机门：登录、短信验证码、滑块/拼图、最终购买确认——一律人工，只过一次，客户端停下等；验证码、密码、密钥绝不进聊天、不进服务端。

### §5.1 流程要落盘，下次直接走

1. 每条跑通的流程（建只读账号、配 CLI、查实例、买机）都要落盘成**机器可执行的 steps 文件（JSON）**，不是给人看的 Markdown。每条流程带入口地址、逐步点击路径、**验证点**和**失效信号**。
2. steps 文件结构（第一批流程库按此写）：
   ```json
   {
     "id": "volcengine.create_readonly_user",
     "version": 1,
     "vendor": "volcengine",
     "entry": "https://console.volcengine.com/iam/user",
     "steps": [
       {
         "step_id": "open_user_create",
         "do": {"action": "click", "match": {"role": "button", "text": "新建用户"}},
         "verify": {"text": "创建用户", "timeout_ms": 10000},
         "fail_when": {"text": "无权限|系统繁忙"},
         "human": false,
         "sensitive": false
       },
       {
         "step_id": "save_access_key",
         "do": {"action": "read_fields", "fields": ["AccessKeyId", "SecretAccessKey"]},
         "verify": {"secret_shown_once": true},
         "human": true,
         "sensitive": true
       }
     ]
   }
   ```
3. **匹配规则只用文本 / 可访问性树（role + name + 文本），不用 CSS 选择器**——控制台改版频繁，CSS 一改就废；文本匹配更接近“人怎么找按钮”。
4. 每一步都必须有 `verify`（怎么算成功）和 `fail_when`（什么情况直接停）；**某步找不到就停下并语音告诉用户，不硬猜、不跳过**。
5. 下次同样操作直接按记录走，不再搜索、不再现找；只有某步失效（页面改版）才回退到搜索，找到后**更新记录并升 version**。
6. 记录存在本地，随客户端走。
7. 附录四家的流程转成 steps JSON 后，作为第一批流程库。
8. 动机实例：2026-11-20 凌晨百度建只读账号时卡住现找，就是因为之前没记录。

## §6 核心流程

### §6.1 找服务器 / 买服务器

1. 用户说想买/想看某台服务器（比如看到 9.9 的）。
2. 客户端检查该厂商只读凭据是否配好；没配好就引导用户去配（§7），配好继续。
3. 客户端查资源、比价、准备购买链接（走 zhao 的优惠链接/代理渠道，见 §8）。
4. 到付款前停下，用户自己确认并付款；买完客户端把实例接进资源列表。

### §6.2 查资源

1. 客户端按厂商 CLI/API 列实例，汇总进资源列表。
2. 已接通的厂商（2026-11-20）：UCloud、京东、天翼云、火山、阿里云、腾讯云、百度云。西部数码见 §9。
3. **多地域口径（2026-11-20 实测）**：
   - 火山：不给 `--region` 时自动先查 `DescribeRegions` 再逐地域列（6 个地域）。
   - 腾讯：不给 `--region` 时自动先查 `DescribeRegions` 再逐地域列（19 个地域，约 30 秒）。
   - 阿里云：仍是**单地域**（默认 cn-beijing），别的地域有机器要显式 `--region`。
   - **客户端在多地域查询期间必须有进度反馈**（“正在查第 N/M 个地域”），否则用户会以为卡死。
4. 字段映射只在有真实实例的厂商上验证过：UCloud（1 台）、阿里云（2 台，均在 cn-beijing）；其余厂商的字段映射待有真实实例后再验。
5. 只读硬闸：host start/stop/reboot 一律拒（exit 2，--yes 也拦）；只读 AK/SK 是第二层保险。

### §6.3 配凭据（核心流程，第一批已跑通）

1. 每家厂商都要一个只读子账号 + AK/SK，存在用户本地，客户端只读本地。
2. 客户端在用户浏览器里打开厂商控制台，语音一步步带用户建只读子账号（只编程访问、只读策略），密钥当场保存进本地配置。
3. 已跑通（2026-11-20 凌晨，zhao 本人操作验证）：火山 muse-readonly（ECSReadOnlyAccess）、阿里云 muse-readonly（AliyunECSReadOnlyAccess，02:13:34 授权）、腾讯 muse-readonly（QcloudCVMReadOnlyAccess）、百度 muse-readonly（自定义 muse_readonly_bcc）。
4. **阿里云 403 定论（2026-11-20）**：不是 key 问题，也不是生效延迟，就是**测试时策略还没授权**。02:13:34 挂上 `AliyunECSReadOnlyAccess` 后重跑 `DescribeInstances` 正常；`host list --provider aliyun` 返回 2 台（均在 cn-beijing），33 个地域扫过只有这 2 台。此项已关闭。
5. 通用提醒：Secret 只显示一次；密钥不贴聊天、不上传。
6. 只读子账号是验证期做法，不是终端用户必需：终端用户用自己的主账号 AK/SK 配厂商 CLI 就行（同 aws configure），想更稳可自建子账号但不强制。

## §7 凭据与安全

1. **vault 是唯一真源**：四家只读凭据全部进 vault（复用现有 srv-vault，AES-256-GCM）；厂商 CLI 自己的配置文件只是**物化缓存**，不算第二份真源。客户端启动/用时才把 vault 里的凭据物化到各 CLI 配置（`ve` / `aliyun` / `tccli` / `bce`），并定义轮换（改了 vault 就重新物化）与清理（退出/删除账号时清掉物化文件）。
2. 备份：vault 主存 + **导出加密备份**，不落明文。
3. 明文风险清单：`Downloads\用户信息.csv`（火山）、`Downloads\新建子用户信息.csv`（腾讯）、`Downloads\AccessKey.csv`（百度）三个明文文件 **2026-11-20 已删除**；桌面 `阿里云.txt` 待删除；西部数码 API 密码在配置页明文显示，勿截图外发。密钥不进聊天、不进服务端、不进截图。
4. **状态回传 schema（定死）**：浏览器扩展回传当前页面/步骤，客户端只按回传状态说话，不猜：
   ```json
   {"url": "...", "page": "...", "step_id": "...", "visible_text_hash": "sha256(...)"}
   ```
   回传**白名单**：只允许以上字段；密钥框、验证码、密码等敏感输入**永远不进回传、不进日志、不进截图**（页面侧做字段黑名单，客户端侧再做一次过滤）。
5. **扩展 ↔ 客户端桥接安全**：本地 WebSocket 只绑 `127.0.0.1`；每次安装生成独立 token；校验 `chrome-extension://<安装 id>` 来源，拒绝其它网页/进程的连接。

## §8 变现：联盟与代理两条线（2026-11-20 zhao 拍板）

1. **联盟优先**（现有）：用户走 zhao 的优惠链接自注册，厂商按首单/注册返佣；轻，无售后责任。阿里云大使、腾讯 CPS 等已有。注意：腾讯 CPS 明确不覆盖 TokenHub，且禁止通过插件/可执行文件静默嵌链接；阿里云大使是唯一确认覆盖模型消费的计划。
2. **代理模式 = 导购 + 托管**（不是纯导购）：zhao 作代理商，用户资源挂在代理账号下，按消费持续返点；重，zhao 是卖方，要担账单与售后。**西部数码单独走代理这条路**。
3. 两条线并存，按厂商分流——有联盟计划的走联盟；无联盟计划的（如西部数码）走代理。客户端按厂商自动选路。
4. 原“服务器只做导购、不代下单”的定位按 §8.2 修订：代理厂商是导购 + 托管，联盟厂商仍是纯导购。
5. 模型不转售：客户端直接用用户自己的厂商 key（BYOK），只收高端增值服务费（多账号、批量、监控）。
